# AplifyAI Mobile

A native Expo/React Native decision surface for AplifyAI engineering managers. It focuses on quick
triage, AI-job visibility, approvals, notifications, and PII access requests—not full administration.

Swipe Jira tickets right to send them **AI-first** and left to keep them **human-first**. Button
fallbacks provide the same decisions and stable `testID` hooks for future Detox coverage.

## Prerequisites

- Node.js 22 and npm
- Xcode/iOS Simulator and/or Android Studio/Android Emulator
- The AplifyAI backend running on port `4000`

## Authentication

- **Demo:** Continue as manager (seeded identity).
- **Social / SSO:** Continue with Google, Apple, Okta, Microsoft Entra ID, or Google Workspace when the
  matching backend env vars are set. Mobile uses `expo-web-browser` and the `aplifyai://auth/callback`
  deep link. See [docs/integrations/FEDERATED_SSO.md](../docs/integrations/FEDERATED_SSO.md).

## Configure the API

Copy `.env.example` to `.env`. The default is `http://localhost:4000/api/v1`, which works from the
iOS Simulator. For the Android Emulator use:

```text
EXPO_PUBLIC_API_BASE_URL=http://10.0.2.2:4000/api/v1
```

Use the development machine's LAN IP for a physical device.

## Run locally

From the repository root:

```sh
npm install
npm run dev:backend
npm run ios -w aplifyai-mobile
# or: npm run android -w aplifyai-mobile
```

After the development client is installed, start later Metro sessions with:

```sh
npm run start -w aplifyai-mobile
```

Native folders generated by `expo run:ios`/`expo run:android` are gitignored.

## Scripts

- `npm run start` — start Metro for an Expo development client
- `npm run ios` — generate/build/run the iOS development client
- `npm run android` — generate/build/run the Android development client
- `npm run lint` — run Expo ESLint
- `npm run typecheck` — run TypeScript without emitting files
- `npm run detox:build:ios` — prebuild and compile the release simulator app
- `npm run detox:test:ios` — run Detox against an already-built app
- `npm run test:e2e` — build and run the complete iOS Detox suite

## Structure

- `app/` — Expo Router routes for splash, login, tabs, ticket detail, and notifications
- `app/(tabs)/` — Triage, Jobs, Approvals, and PII Firewall manager tabs
- `src/api.ts` — native API client with an injectable absolute base URL
- `src/session.tsx` — bearer session persisted with Expo SecureStore
- `src/ui.tsx` — native theme primitives and async-state helpers
- `../shared/types.ts` — shared backend contracts; the web API client remains unchanged

## Detox E2E

The Detox suite uses an Expo prebuild and a release iOS Simulator binary, so Metro is not required.
The backend is required and should start from fresh, non-persistent seed data because the manager
journey intentionally changes triage and approval state.

From the repository root:

```sh
npm install
AUTH_ALLOW_DEMO_LOGIN=1 \
AUTH_SESSION_SECRET=detox-local-session-secret-at-least-32-characters \
npm run start -w aplifyai-backend
```

In another terminal:

```sh
npm run test:e2e:mobile
```

To build and test separately:

```sh
npm run detox:build:ios -w aplifyai-mobile
npm run detox:test:ios -w aplifyai-mobile
```

The default simulator is `iPhone 16`. Override it when that runtime is not installed:

```sh
DETOX_IOS_DEVICE="iPhone 15 Pro" npm run test:e2e:mobile
```

Requirements are Xcode with an installed iOS Simulator runtime, CocoaPods, Node.js 22, and the
backend on `http://localhost:4000/api/v1`. Generated `ios/` files and Detox artifacts remain
untracked. Android is not configured because the current Expo SDK 57-compatible Detox config
plugin is unavailable; the prebuild-based iOS lane is the supported local and CI path.

Covered stable IDs include:

- `login-primary-button` (Continue as demo)
- `login-google`, `login-apple`, `login-okta`, `login-entra`, `login-google_workspace`
- `triage-ai-button`, `triage-human-button`
- `triage-open-ticket-button`, `triage-swipe-card`
- `tab-triage`, `tab-jobs`, `tab-approvals`, `tab-pii`
- `approval-approve-<id>`, `approval-reject-<id>`
- `pii-request-access-button`
- `notifications-button`, `notifications-mark-all-button`

The suite is button-first. A representative swipe test is present but skipped by default; enable it
only when validating gesture behavior on a known-stable simulator/runtime combination.
